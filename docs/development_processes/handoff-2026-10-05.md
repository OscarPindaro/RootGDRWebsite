## Known issue to revisit later (Oscar's note)

At the end of this deployment cycle, reconsider whether pinning the helper and
PostgreSQL tool images by **digest reference** is worth it. The current design
pins each tool twice — by digest in the source constants and by immutable image
ID at transfer time — and a target that received the image as a transferred
archive holds it only by ID. That is why `CaptureSpec.helper_image`,
`DeploymentPlan.helper_image_id`, `CurrentDeployment.helper_image_id` and
`VikunjaPlan.helper_image_id` exist, and why `capture`, `capacity` and the board
bootstrap all take the resolved ID. The first live rollout failed on exactly
this mismatch after downtime.

Keep it as it is for now: it works and it is verified. When the cycle ends,
decide deliberately between (a) keeping both pins, (b) pinning only the
immutable image ID everywhere and dropping the digest references, or (c)
tagging transferred images on the target so the digest reference resolves
again. Do not change it as a side effect of another ticket.

## Environment notes learned the hard way

- The artifact is built from `git archive` of the selected commit, so a ticket's
  code must be committed before its disposable rollout test can pass.
- `harness env up` rewrites `config.test.yaml`; never stage that file.
- Podman can chown a named volume's root even on a read-only mount. Runtime
  binds use the canonical mountpoint of an existing volume instead.
- Restic snapshots are tagged `rootgdr-managed-v1`, `application=<name>`,
  `purpose=<weekly|predeploy>`, `run=<uuid>`. Retention only ever touches
  `purpose=weekly` snapshots of one application, and only after a new verified
  copy exists.
- The tests leave `/tmp/pytest-of-oscar/garbage-*` directories behind when a
  restored volume contains container-owned files; that is cosmetic.
